# Бот поддержки на nano-vm: архитектура пилота (черновик)

Статус: проект. В этом репо реализована демо-эскалация (витрина → оператор с резюме).
Документ описывает, как она превращается в отдельный пилот поверх `llm-nano-vm` и
`nano-vm-mcp`, и какие швы в коде уже оставлены.

Принцип пилота: **LLM генерирует текст, а право на переход состояния (одобрить, отказать,
передать человеку) принадлежит конечному автомату.** Все решения исполняются программой ВМ
с детерминированным трейсом и receipt.

## 1. Границы и выбор рантайма

- Пилот — **отдельный репозиторий**. Он использует пакет `llm-nano-vm` (ядро) и шлюз
  `nano-vm-mcp` (`vm_step`, хранение сессий и трейсов).
- `app/runtime` в этом репо — собственная, более простая ВМ главного бота (DSL v0.1, planner
  генерирует программу). **В пилот она не переносится**: критичный путь поддержки не должен
  зависеть от программы, составленной LLM. Программы пилота — статические, написанные заранее.
- Витрина-демо остаётся как есть (ответ строго по корпусу, без planner); её логика становится
  первым сценарием программы пилота.

## 2. Что уже есть в демо и во что превращается

| Сегодня (nano-vm-bot) | Роль | В пилоте |
|---|---|---|
| `app/core/dialog.py` — `DialogHistory` (`add/recent/clear`) | история диалога в памяти процесса | тот же интерфейс, реализация поверх БД |
| `app/core/handoff.py` — `build_summary`, `render_transcript_html` | резюме и карточка, без зависимости от Telegram | переносится как есть, вызывается из tool |
| `app/core/operator.py` — `OperatorSession` (+`summary`), `list_open_sessions` | клиент ↔ тема, статус | вырастает в `tickets` |
| `app/core/support_events.py` — `on / emit` | события `opened / summary / closed` | вход для SSE веб-интерфейса |
| `app/handlers/operator.py` | Telegram-транспорт оператора | адаптер канала |

## 3. Слои

```
 канал (Telegram / Web)            адаптер: receive → vm.step → send; ядро видит только vm.step()
        │
 vm_step(session_id=ticket, input) nano-vm-mcp: хранит сессию и трейс, возобновляет suspend
        │
 Program (JSON, статическая)       FSM: шаги LLM / TOOL / CONDITION
        │
 tools                             поиск по корпусу и памяти, тикеты, заметки, уведомления
        │
 внешнее состояние                 БД тикетов, векторное хранилище памяти клиента
```

Следствие: бизнес-логика (тикеты, память, резюме) не знает про aiogram; Telegram и веб —
адаптеры одного и того же `vm_step`.

## 4. Программа сценария «вопрос по базе знаний с эскалацией»

Идентификаторы шагов иллюстративны; точные поля шага сверять с версией ядра.

| # | Шаг | Тип | Что делает |
|---|---|---|---|
| 1 | `search_corpus` | TOOL | поиск по корпусу; результат — числовой сентинел 0/1 (`found`) |
| 2 | `gate_found` | CONDITION | `$found > 0` → ответ; иначе → предложение эскалации |
| 3 | `answer` | LLM | ответ строго по найденным фрагментам (текст — данные) |
| 4 | `offer_escalation` | TOOL | показывает кнопку «Позвать оператора»; **suspend**, сентинел `AWAITING_CONSENT` |
| 5 | `gate_consent` | CONDITION | согласие клиента → открыть тикет; иначе завершить |
| 6 | `open_ticket` | TOOL | создаёт тикет и тему оператора; при ошибке — `raise` |
| 7 | `summarize` | LLM | резюме для оператора (`on_error` — продолжить без резюме) |
| 8 | `post_card` | TOOL | карточка и резюме в тему оператора |
| 9 | `await_operator` | TOOL | **suspend**, сентинел `AWAITING_OPERATOR`; возобновление по ответу или `/close` |
| 10 | `close_ticket` | TOOL | закрывает тикет, пишет итог в память клиента; terminal |
| 11 | `notify_client` | terminal | уведомление клиента |
| – | failure terminal | terminal | достижимый терминал ошибки (требование валидатора) |

Для сценариев с политикой (возврат, скидка) тот же каркас: `classify_intent[LLM]` →
`normalize_output[TOOL]` → `policy_gate[CONDITION]` → `approve | deny | escalate[TOOL]` →
`notify`. Право одобрить принадлежит гейту, а не модели.

Правила DSL, которые программа обязана соблюдать:
- классификация свободного текста — через TOOL `normalize_output(text, keywords)`, а не
  `allowed_outputs`;
- в условиях нет вызовов методов, арифметики и скобок; `and`/`or` вычисляются слева направо
  без приоритета — условия держим простыми, по одному оператору;
- `PENDING` зарезервирован под suspend; свои сентинелы — `AWAITING_*`/`REQUIRES_ACTION`;
- **каждый suspend-gate — отдельный шаг**: возобновление всегда продвигает указатель за
  суспендированный шаг, повторный suspend на том же шаге потеряет вывод;
- перед каждым запуском — `ProgramValidator(program).validate().is_valid()` (движок сам не
  валидирует); валидатор проверяет недостающие цели, недостижимые шаги, циклы.

## 5. Tools и границы

- Tool, пишущий во внешнюю систему, **не открывает собственную сессию**: сессия передаётся
  замыканием при регистрации tool в ВМ (не через args/context шага — не сериализуется в трейс).
  Commit — на границе вызывающего сервиса/адаптера, не внутри tool. Иначе при падении tool N+1
  после успешного commit tool N receipt остаётся формально верным, но не отражает расхождения.
- Терминальный tool при ошибке делает `raise`. Возврат сентинела без CONDITION-потребителя
  не помечает трейс как FAILED.
- `client_id`, `ticket_id` и подобные идентификаторы берутся из контекста сессии, а не из вывода
  LLM или args, пришедших от модели (тот же принцип, что принудительная подстановка `user_id`).
- Ядро не управляет транзакциями внешних систем — это его осознанная граница, а не пробел.

## 6. Receipt, резюме и память — три разных артефакта

| Артефакт | Источник | Свойства |
|---|---|---|
| **Receipt** | проекция трейса | детерминирован, пересчитываем, без LLM-генерации; в тикете хранится `trace_id` и `trace_hash` |
| **Резюме** | LLM | поддерживающий текст для оператора; хранится в `tickets.summary` с пометкой «сгенерировано»; **не** часть receipt |
| **Память клиента** | закрытые тикеты | RAG по прошлым обращениям клиента; читается только tool-ом с `client_id` из контекста |

Решение по LLM-резюме: оно полезно, но недетерминировано, поэтому живёт отдельным слоем
рядом с receipt, а не внутри него. Тот же подход, что у слоя пояснений поверх receipt:
`{решение, причина, правила, trace_ids}`.

## 7. Данные

Сессии ВМ и трейсы уже хранит `nano-vm-mcp` (`vm_sessions`, `execution_traces`). Пилот их
**не дублирует**: тикет ссылается на `execution_id` и `trace_id`.

**clients** — `id`, `channel`, `channel_user_id` (UNIQUE с channel), `display_name`,
`consent_at`, `forgotten_at`, `created_at`.

**tickets** — `id`, `client_id`, `status` (`open | pending_client | closed`), `assignee_id`,
`summary`, `resolution`, `execution_id` (сессия ВМ), `trace_id`, `trace_hash`,
`telegram_thread_id`, `opened_at`, `first_response_at`, `closed_at`.
Не более одного открытого тикета на клиента (частичный UNIQUE).

**messages** — `id`, `ticket_id` (NULL до эскалации), `client_id`, `role`
(`client | bot | operator | system`), `kind`, `body`, `sources` JSON, `internal` (заметка
оператора — не уходит клиенту и в память), `attachments` JSON (только `file_id` и метаданные;
файлы не храним), `created_at`.

**ticket_events** — аудит: `ticket_id`, `actor`, `type`, `payload`, `created_at`.
**operators** — `id`, `telegram_id`, `role`, `active`, `web_token_hash`.
**kb_promotions** — пары «вопрос → ответ», предложенные в общую базу знаний, и их статус.

Срок хранения (`retention_days`) и `/forget` (сообщения, векторы, обезличивание клиента) —
в первом релизе, а не позже.

## 8. Память клиента (RAG)

- Одна коллекция Chroma `client_cases` с метаданными `client_id`, `ticket_id`, `created_at`.
  **Изоляция:** единственная функция `search_client_memory(client_id, query)` всегда добавляет
  фильтр; прямого доступа к коллекции из tools и хендлеров нет. Тест изоляции обязателен.
- Запись при закрытии тикета: резюме, итог и ключевые пары «вопрос → ответ»; внутренние
  заметки не включаются.
- Выдача — как данные в разделителях (`<client_history>…</client_history>`), бюджет ~1500
  токенов. Реплики клиента и оператора — недоверенный текст: инструкции внутри них не
  исполняются.
- Общая база знаний пополняется только через одобрение оператора; автоматического переноса
  из клиентской памяти нет (защита от отравления корпуса).

## 9. Веб-интерфейс как второй адаптер

Веб не добавляет логики: это канал `receive → vm_step → send` для той же программы,
и receipt по одному сценарию из Telegram и из веба имеет идентичную структуру.

- Чтение: `GET /api/tickets?status=open`, `GET /api/tickets/{id}` (сообщения, резюме, заметки,
  события, `trace_id`), `GET /api/clients/{id}`.
- Действия: `POST /api/tickets/{id}/reply` (адаптер доставляет клиенту), `/note`, `/assign`,
  `/close`, `/promote`. Ответ оператора — вход `vm_step` для возобновления `await_operator`.
- Живые обновления: SSE `GET /api/stream` поверх `support_events`.
- Доступ: вход операторов через Telegram Login, роль из `operators.role`. Веб не видит ключей
  и настроек бота.

## 10. Совместимость и зависимости

- `llm-nano-vm`: на текущий момент 0.8.9 на PyPI. Строгий токенизатор условий (в релизе 0.8.10)
  отвергает условия, которые раньше проходили с молча отброшенными символами — условия
  программы пилота нужно прогнать на нём заранее.
- `litellm` — верхний пин `<1.98.0` (иначе падает Python 3.10).
- `mcp` — верхний пин `<2` в связке с `nano-vm-mcp` (2.x меняет серверный API); у главного
  бота диапазон шире, пилот должен следовать пину шлюза.
- Python: матрица CI ядра 3.10–3.12. Главный бот сужен до 3.12 из-за `sqlalchemy>=2.1`.
  Для пилота нужно выбрать: `sqlalchemy<2.1` (тогда 3.10 остаётся) или матрица только 3.12.
- Известный дефект шлюза: отмена в середине возобновления suspend-сессии «отравляет» сессию
  (повторный шаг отвечает «уже возобновлено»). Тикет-сессии с suspend подвержены ровно этому;
  до исправления возобновление выполнять под защитой от отмены.

## 11. Риски

- Сохранённые реплики возвращаются в промпт → инъекция. Смягчаем разделителями, правилом
  «данные, не инструкции» и тестами.
- Утечка между клиентами в памяти → единственная точка доступа с фильтром и тест.
- Хранение чужих переписок → согласие, срок хранения, `/forget`; юрисдикция клиентов
  определяет требования (например, 152-ФЗ). Это не юридическая консультация.
- Недетерминированное резюме принимают за «официальный» итог → пометка «сгенерировано»,
  receipt остаётся отдельным.

## 12. План

1. Каркас репо, зависимости, валидатор на старте, программа FAQ + эскалация на `MockAdapter` — 2–3 дня.
2. Канальный адаптер Telegram: клиент и операторская группа, suspend/resume через `vm_step` — 2 дня.
3. Тикеты, сообщения, события; связь с `execution_id`/`trace_id` — 2 дня.
4. Память клиента, `/promote`, тесты изоляции — 2–3 дня.
5. Приватность: согласие, retention, `/forget` — 1 день.
6. Веб-адаптер (REST, SSE, SPA) и проверка идентичности receipt — 5–8 дней.
7. Демо-упаковка: receipt для одного успешного и одного отклонённого прогона — 1–2 дня.

Оценки приблизительные, не замеры.
